Find code that could be written better. Use `--fix` to apply the fixes.

## Usage

```bash
pun lint [paths] [options]
```

```bash
pun lint                         # report problems
pun lint --fix                   # apply fixes
pun lint -A lint/style           # turn a group off for this run
pun lint --max-warnings 10       # fail on more than 10 warnings
pun lint --generate-baseline     # accept current problems
```

## Options

| Option | Description |
| --- | --- |
| `--fix` | Apply the fixes. Skips rules with `fix = "off"`. |
| `--generate-baseline [<file>]` | Save every current problem to a baseline and exit 0. Default file: `[lint] baseline`, else `pun-lint-baseline.toml`. When a file fails (a syntax error, say), nothing is written and the run says so. |
| `-A`, `--allow <rule>` | Turn a rule or group off. |
| `-W`, `--warn <rule>` | Turn a rule or group on as a warning. |
| `-D`, `--deny <rule>` | Turn a rule or group on as an error. |
| `--deny-warnings` | Fail on any warning. |
| `--max-warnings <n>` | Fail on more than `n` warnings. |
| `--concise` | One line per problem. |
| `--format=<fmt>` | Report as `json`, `checkstyle`, `junit`, `gitlab`, `github` or `agent`. |
| `--no-cache` | Check every file again. |
| `-q` | Print nothing. The exit code gives the result. |

Lint also takes the file options of [`pun format`](/docs/commands/format#options), such as `--dirty`, `--staged` and `--diff`.

## What happens

- Reads the `[lint]` preset, sets and rules from `pun.toml`.
- Checks each file and prints the problems.
- With `--fix`, edits the files. It does not format them, so use `pun check --fix` for both.
- Only `error` rules fail the run. `warn` rules only report.
- Hides problems listed in the baseline (`[lint] baseline`), after `@pun-ignore` comments. Each entry is a file, rule, message and count, without a line, so moving code keeps it hidden. Entries nothing matches any more get a note. `--fix` still fixes what the baseline hides. Without `--fix`, a file's diff leaves out the changes of the rules the baseline hides there.
- Reads standard input (`-` or `--stdin-filename`) only with `--fix`, and prints the fixed code. Without `--fix`, standard input is a run error (exit 2): pass the files to check instead.
- Skips Blade, `vendor/`, `bootstrap/cache`, `build`, `node_modules` and `storage`.

```toml pun.toml
[lint]
preset = "recommended"

[lint.rules]
"style/require-final-class" = "error"
"types/no-loose-comparison" = { level = "warn", fix = "off" }
"style/no-short-ternary" = "off"
```

```toml pun.toml
[lint]
baseline = "pun-lint-baseline.toml"
```

To ignore one line, add `// @pun-ignore <rule> -- <reason>`. See [ignore comments](/docs/configuration/ignore-comments).

## Limitations

- Pun doesn't have every Rector and PHP-CS-Fixer rule yet. The [rule reference](/docs/rules/lint) marks the missing ones as Planned.
- A group turns on only the rules Pun has. Naming a Planned rule directly is a config error.
- Rules from PHP-CS-Fixer accept only `@pun-ignore-file`, not line or region ignores.
- An overriding method gets a return type only when both classes are in `vendor/`, or both are outside it.
- Rules from PHP-CS-Fixer report a file, not each place they would change, so their baseline entries count files: a new problem in a file the baseline lists for that rule stays hidden.
- The lint baseline is separate from `[analyse] baseline`. `pun check` reads both.

## Exit codes

| Code | Meaning |
| --- | --- |
| 0 | No errors. |
| 1 | Errors, or too many warnings. |
| 2 | Pun could not run. |
